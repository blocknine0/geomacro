# Signed data recovery and website release order

Recovering current B2/D1 data must not first require republishing an unchanged website. The GRI and downstream Risk Indices producers now require a trusted protected-main event, exact checkout/event SHA and current remote canonical main before any B2/D1 operation. A moved or unverified main fails before quota consumption.

No source permission, independent reviewer signature, country certificate, fresh original, historical B2 pin, GRI numerical computation, archive readback or D1 proof requirement changes. A canonical-code admission receipt explicitly does not attest an approved input or signed product. It cannot create a publication package or reviewer authority.

After a successful actual signed-data producer, the existing Production Website Health workflow runs independently on the same trusted main. Only manual/repository publication events or the successful downstream Indices continuation are accepted; ordinary tests-only pushes, PRs, failed runs, forks and stale-head runs do not qualify. Its exact website SHA, Lovable mirror parity and default signed-product deep-health checks stay strict. A stale website or missing product still fails final acceptance. Website failure no longer changes a successful producer's result or triggers redundant B2 publication retries.

This resolves a release-order dependency, not missing real approvals. The owner-provided October 17 candidate dossier is not an approved current signed publication; sample delivery ZIPs are not production inputs. No copied sample, new timestamp, synthetic signature, disabled source gate or fabricated score may fill that gap. Supabase stays frozen; payments remain unauthorized.
