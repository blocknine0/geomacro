# Production B2/D1 runtime acceptance (no Supabase, no new paid services)

## Phase 2B protected runtime readback after governed edge recovery (#3154)

The main-only, no-funds B2/D1 acceptance workflow also runs automatically on canonical `main` pushes to this operations document. This section records why an explicit bounded production probe is needed following the merge of [#3154](https://github.com/blocknine0/geomacro/pull/3154) (squash commit `0a8fea1e045219cbf55ef78317c9ee4cdf942815`): both public B2 Workers had previously returned HTTP 503, and CI alone cannot prove provider B2 PUT/GET, SHA-256 bytes, and D1 quota receipts. A documentation-triggered push is an existing authorized workflow event, not a new endpoint, external payment, or override of the manual `VERIFY_EXISTING_B2_D1_ONLY_NO_FUNDS` confirmation contract. It runs the existing eight-attempt-budget diagnostic in the existing `production` GitHub Environment. Never treat its offline job as production acceptance, and never manually enter credentials into logs or artifacts.

**Acceptance is deliberately separate:** Require the real `production-runtime-read-write-readback` job's PASS receipt, nonzero GET/PUT D1 ledgers, exact immutable diagnostic object hash and second independent GET. This diagnostic probes B2/D1 configuration only; it does NOT independently sign current public evidence, promote a D1 signed-hot product, establish both edge source freshness, prove the deployed Worker revision, or authorize x402 payments. Retain HTTP 503 for unavailable signed material. If this job fails, classify its error from redacted job evidence and use the existing owner-only production Environment/Backblaze/Cloudflare controls to repair the actual dependency; do not change PREDGE, historical data, source rights, pricing, settlement, or quota limits.

## What this verifies

The local owner preflight is **not** a view of GitHub Environment secrets or Cloudflare runtime state. A local `NOT_PROVIDED` only describes that shell. It cannot diagnose production credential presence or production writes.

The protected workflow `.github/workflows/production-b2-d1-runtime-readwrite-acceptance.yml` checks real runtime behavior on canonical `main` only. It uses existing GitHub Environment `production` credentials and the existing `geomacro-control-plane` D1 database; it does not create another database, subscription, Worker, or paid dependency.

The no-user-data probe writes one tiny private diagnostic JSON object to the existing Backblaze B2 bucket `geomacro-private-archive`, reads its full bytes back once as part of `putWithMetadataVerification`, then performs a second independent GET. It compares exact byte length and SHA-256. Each B2 attempt must reserve the existing shared daily quota through Cloudflare D1. The workflow also calls the deployed Control Plane's authenticated `GET /v1/b2-quota/status` before and after the probe using the same HMAC bearer contract used by the publishers. It verifies the Worker-visible D1 counters advance too, then independently reads the per-run `b2_request_quota_workflow_receipt` rows through the Cloudflare D1 API and confirms GET/PUT receipts and before/after counter movement. Thus both the direct D1 credentials and the deployed Worker token/binding path are exercised. No HEAD request is used. It does not delete the diagnostic object; deletion would add another production request and is intentionally not part of the probe.

The workflow output is a **B2/D1 runtime configuration test**, not a signed-product readiness claim. A PASS does not say that current Intelligence, Global Risk, Risk Indices, the source/legal rights, independently signed Facts/Rights, current numerical GRI, country/category certificates, or public deep health are ready. The legacy `/api/health?deep=1` must remain fail-closed until its own real current signed-data requirements pass. The probe never updates public hot snapshots.

## Owner-only configuration

Open GitHub **Settings → Environments → production → Environment secrets** for `blocknine0/geomacro`. Verify the following names exist in the environment actually used by the protected publishers (add only if missing). Never copy values into a PR, issue, chat, artifact, or Actions logs.

- `B2_KEY_ID`
- `B2_APPLICATION_KEY`
- `CLOUDFLARE_ACCOUNT_ID`
- `CLOUDFLARE_API_TOKEN`
- `GEOMACRO_COMMERCE_LEDGER_TOKEN`

The Cloudflare API token must be able to list the existing D1 database and execute D1 queries (read/write) for `geomacro-control-plane`. Use the narrowest existing account-level D1 Read and D1 Write/Edit scopes required for database listing and the D1 query endpoint; do not grant unrelated service permissions. The `GEOMACRO_COMMERCE_LEDGER_TOKEN` must be the existing control-plane ledger root used by the protected publishers (at least 32 characters); the probe derives the existing HMAC bearer and verifies it against the deployed `/v1/b2-quota/status` endpoint. It never prints the token or derived bearer. The deployed Cloudflare Worker has a separate secret named `CONTROL_PLANE_TOKEN`; the existing `Deploy D1 Control Plane` workflow derives and installs it from the same root. A missing root token is reported by name only, and `401`/auth-unconfigured/Worker D1-binding errors fail closed. If the live test returns `CONTROL_PLANE_TOKEN_MISMATCH`, do not paste or manually expose either value: review the existing GitHub production Environment secret `GEOMACRO_COMMERCE_LEDGER_TOKEN`, then use **Actions → Deploy D1 Control Plane** on canonical `main` to resynchronize the derived Worker secret only after its required distinct `PREDGE_RESEARCH_NEWS_TOKEN_OVERRIDE` is configured and valid. That deployment workflow deliberately fails closed without the Predge rotation prerequisite; do not bypass that check or change Predge's secret as part of this PR. The runtime test intentionally fails if that token has only metadata/read-only access or points to the wrong account/database. Do not create a new database or expand permissions beyond the existing account/database scope needed by the protected workflow.

`D1_DATABASE_ID`, `B2_ACCOUNT_QUOTA_REQUIRED`, `B2_ACCOUNT_QUOTA_WORKFLOW_ID`, and `B2_REQUEST_BUDGET` are set/resolved by the workflow; they are not owner secrets. The probe fixes the budget at 8 attempted B2/native-read requests and fails before B2 I/O when the existing D1 quota ledger lacks safe headroom. The actual B2 calls are independently counted in D1. It writes only a nonce-bearing diagnostic object in the private `geomacro-evidence/v1/private/runtime-config-acceptance/` prefix, not publisher material or customer data.

For the **separate historical GRI file-version recovery** (not the basic B2/D1 probe), the existing workflow needs the distinct read-scoped pair `B2_ARCHIVE_READ_KEY_ID` and `B2_ARCHIVE_READ_APPLICATION_KEY`. Keep that pair limited to its intended history read scope; do not substitute the general B2 write key just to satisfy presence checks. The normal content publishers separately require their already configured public-key pins and genuine inputs. This probe does not repair missing signatures, grants, GRI scoring, or expired hot snapshots.

## How to run and interpret

- A merge of this PR to `main` triggers the one-shot production acceptance job after the offline tests pass. The job uses the GitHub `production` Environment and any configured environment approval policy.
- An owner may also run **Actions → Production B2-D1 Runtime Read Write Readback Acceptance → Run workflow** on `main`, entering exactly `VERIFY_EXISTING_B2_D1_ONLY_NO_FUNDS`.
- A green config-presence check is insufficient. Accept only a run containing `status: PASS`, `b2_put_verified: true`, `full_body_readback_verified: true`, `second_independent_get_verified: true`, `d1_quota_write_readback_verified: true`, `authenticated_control_plane_d1_readback_verified: true`, nonzero per-run GET and PUT receipts, advanced D1 counters visible from both direct D1 and the deployed Worker, `supabase_requests: 0`, and `payment_attempts: 0`.
- If an owner secret is missing, the job prints its **name only** and the user should add it to the `production` Environment secrets above. If D1 listing or D1 query is rejected, verify the token's account and D1 Read/Write scope. If the authenticated Worker status GET is unauthorized, verify the existing `GEOMACRO_COMMERCE_LEDGER_TOKEN` corresponds to the deployed Control Plane's configured `CONTROL_PLANE_TOKEN` by using the same existing secret already used by production publishers; do not rotate the root token impulsively, and do not paste any value or bearer token into logs. If B2 PUT/GET is denied or the provider's quota is exhausted, a variable cannot cure it: retain the failed receipt and resolve the existing account key scope/actual provider quota through the current owner account, without enabling paid infrastructure. Do not bypass the D1 quota governor or retry in a loop.

## Safety boundaries

No Supabase variables are injected; a Supabase or payment environment contaminant fails closed. No x402, Coinbase settlement, funds, source article, signed proof, original URL, license, or private key is read/written. The probe's only persistent data is the private diagnostic B2 object and the normal existing D1 request/counter ledger records. This is a bounded production write/read/readback because a no-network/unit/metadata-only test cannot establish that production credentials really work.
