# Geomacro GOAT x402 Partner Pilot

Status: **ISOLATED PARTNER / FUNDING / REVENUE PILOT — NOT GENERAL BILLING**

## Objective

Build one production-shaped GOAT Flow / x402 integration that lets an AI agent pay for a real Geomacro verified-intelligence service and receive a signed structured risk result after server-side payment confirmation.

Commercial goals:

1. qualify Geomacro for GOAT ecosystem funding/support;
2. create a credible path to an official GOAT ecosystem partnership/listing;
3. prove repeatable machine-to-machine paid intelligence usage;
4. create Geomacro's first attributable machine-service revenue only after a real production settlement is completed and reconciled.

Geomacro remains **Verified Intelligence & Decision Infrastructure**. GOAT is a partner distribution/payment rail, not the company identity.

## Upstream HMAC security boundary

GOAT's documented HMAC canonicalization is a legacy delimiter format (`key=value&...`) and the official reference states that it is not injective for unrestricted values containing `&` or `=`.

Geomacro therefore must not pass unrestricted customer strings into HMAC-signed top-level merchant request fields.

The partner pilot uses strict allowlisted/scalar formats for signed order fields:

- deterministic safe `dapp_order_id` generated by Geomacro;
- numeric chain ID from trusted environment/runtime capability;
- token symbol/contract from trusted GOAT merchant/order capability, not free-form user text;
- EVM payer address validated as a 20-byte hex address;
- decimal-integer atomic amount;
- no customer-controlled callback calldata in the initial DIRECT pilot.

The initial pilot uses public merchant `DIRECT` only. Operator-provisioned callback/delegate compatibility is out of scope.

## Order state model

Geomacro recognizes the current official GOAT statuses:

- `CHECKOUT_VERIFIED`
- `PAYMENT_CONFIRMED`
- `INVOICED`
- `FAILED`
- `EXPIRED`
- `CANCELLED`

Classification:

- `PAYMENT_CONFIRMED` → trusted paid state.
- `INVOICED` → trusted successful terminal state; a poller may observe this without first seeing `PAYMENT_CONFIRMED`.
- `CHECKOUT_VERIFIED` → not paid; never fulfill.
- `FAILED`, `EXPIRED`, `CANCELLED` → terminal non-fulfillment states.
- unknown future status → fail closed; never fulfill automatically.

## Fulfillment invariants

Before Geomacro releases paid intelligence, the backend must independently verify all of these:

1. order was read from the authenticated GOAT merchant API;
2. status is exactly `PAYMENT_CONFIRMED` or `INVOICED`;
3. `order_id` matches the persisted provider order;
4. `dapp_order_id` matches the persisted Geomacro order identity;
5. payer address matches the expected buyer address;
6. chain ID matches the expected trusted order challenge/capability;
7. token contract/symbol matches the expected trusted order challenge/capability;
8. atomic amount matches the persisted order amount;
9. transaction hash exists where the target GOAT deployment provides it for confirmed settlement;
10. the Geomacro request has not already been fulfilled under a conflicting provider settlement;
11. the Risk Object / Risk Gate response remains valid under its own verification and freshness rules;
12. `execution_authorized=false` before and after fulfillment.

A browser callback or UI success state is never sufficient for fulfillment.

## Proof semantics

The GOAT `/proof` response must not be marketed as a cryptographic provider signature.

The official reference states that its historical `signature` field is a recomputable Keccak256 digest over selected payment fields and does not cover `status`.

Therefore:

- backend authenticated order status is the operational fulfillment signal;
- proof may be stored as reconciliation evidence;
- where independent settlement proof is required, verify the transaction hash on the relevant production chain/RPC and reconcile the ERC-20 transfer rather than trusting the field name `signature`.

## Runtime architecture to build

### Merchant server

A new GOAT-specific server module owns:

- environment/config validation;
- HMAC auth signing;
- strict request-field validation;
- bounded HTTP timeout/retry behavior;
- order creation;
- authenticated order status read;
- optional proof read after trusted success;
- cancellation where allowed;
- safe error mapping and secret redaction.

Merchant API credentials never enter browser/client code.

### Order orchestration

The orchestration service must:

1. create/reuse one Geomacro `agent_api_requests` request;
2. acquire the existing durable GOAT external-order creation claim;
3. generate one deterministic safe `dapp_order_id`;
4. mark provider creation attempted before the external create-order call;
5. persist authoritative challenge/order fields;
6. never re-create an order after an ambiguous provider-creation failure without explicit reconciliation;
7. verify settlement through authenticated order status before fulfillment;
8. write one provider payment reference and one fulfillment record;
9. make exact retries return/reconcile the same paid intelligence result;
10. fail closed on field/status mismatch.

## Buyer/client boundary

The buyer or autonomous agent controls its own wallet/payment transaction.

Geomacro must not:

- hold buyer private keys or seed phrases;
- sign the buyer's wallet payment;
- automatically execute a later financial action because Risk Gate returned `ALLOW`;
- rebroadcast a second payment after an ambiguous wallet/provider error without reconciliation.
